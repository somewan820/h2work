# 工作流概念与项目上下文

本工作流跨项目、跨技术栈复用。通用规范负责确定流程与约束，项目专属说明补充实际命令、环境和职责；若已有项目约定与通用规范存在差异，应明确记录适用方案。

## 基本概念

- 大需求：一个完整业务目标，是版本发布单位，可以包含多个开发任务。
- 开发任务：可独立实现和验收的工作单元，是开发分支、worktree 和任务 PR 的单位。
- 集成完成：开发任务经 PR 合入 dev；发布完成：大需求对应的版本实际发布并验证成功。

文档中的 TASK-123、REQ-100 等编号仅为示例，实际沿用目标项目的任务与大需求标识。

## 完整交付流程

1. 明确关联 issue、所属大需求、开发任务职责和验收目标，按改动范围确定检查清单。
2. 按 Git 工作流创建或恢复任务分支和独立 worktree，在对应目录开发和验证。
3. 按提交规范完成提交，rebase 最新 dev，验证后按独立的 pr skill 创建任务 PR。
4. 完成独立审查和适用的合并检查，按规范整理最终提交信息，以 Squash and merge 合入 dev，并记录任务提交 SHA。
5. 一个大需求完成后，按发布工作流从最新 main 准备独立发布分支和 worktree，依据清单 cherry-pick 对应任务提交及必要依赖。
6. 对实际发布组合重新验证、验收和独立审查，通过发布 PR 合入 main，再按项目流程发布并记录结果。

只执行当前请求涉及的阶段，具体命名、操作顺序、证据和完成标准以对应主题规范为准。

## 项目提供的信息

- 实际远端、任务与大需求标识，以及当前 issue 或 PR 的职责与验收要求。
- 项目现有的构建、验证命令、CI 必过任务和运行环境。
- 代码托管平台上的 main、dev 分支保护、审查要求及 dev 的合并方式。
- 项目现有的发布方式和授权范围。

规范不自动创建分支或配置平台规则，实际配置按目标项目的既有流程完成。

## 尚未统一确定的事项

以下内容暂未制定通用默认，使用目标项目已有的明确约定；缺失且影响当前操作时，再补充确认：

- 需求与 issue 模板、任务拆分规则、编号来源和生成方式。
- 发布分支命名、版本号与 tag 规则。
- 发布 PR 合入 main 的具体合并方式。
- 最终合并、发布的负责人及授权范围。
