# 合并前检查规范

开发任务 PR 合入 dev、发布 PR 合入 main 前，必须通过适用于本次改动的检查。检查分为基础必过项、按改动触发的专项检查和发布 PR 追加检查，范围围绕 issue 的职责、验收要求及直接影响。

## 检查清单与项目配置

- 尽早根据任务范围和影响确定检查清单。后续随实际新增影响调整，不在临近合并时追加无关检查。
- 各项目明确检查名称、具体命令或 CI 任务、适用改动范围、运行环境与通过标准，沿用项目已有工具和流程。
- 通用规范规定检查类别与触发条件；全量测试范围和覆盖率目标由项目明确，不统一设定覆盖率百分比，也不要求每个改动都运行全仓端到端测试。

## 开发 PR 的基础必过项

1. 范围与分支正确：关联任务明确，差异仅包含本任务及必要依赖，已 rebase 最新 dev，没有冲突，提交信息符合规范。
2. 构建与静态检查通过：执行项目已有的构建、类型检查、lint 和格式检查，覆盖受影响模块。纯文档变更执行文档相关检查，例如链接与命令示例核对；涉及构建配置时仍需验证对应构建。
3. 相关测试通过：执行受影响功能的测试。新增或修改业务行为时，提供有针对性的测试或可复核的验收证据；修复 bug 时，优先补充能复现问题的回归测试。
4. 任务验收完成：逐项对应 issue 的验收标准给出实际验证结果，确认交付行为符合需求。
5. 独立审查通过：按 [代码审查与合并准入](code-review.md) 完成交叉验证和对抗性审查，没有未解决的有效阻塞项或必要验收的待验证项。

范围核对、任务验收与独立审查适用于所有开发 PR。工具检查和测试的适用范围按实际改动确定，测试质量遵循 [开发与实现原则](development.md)。

## 按改动触发的专项检查

- 接口或公共模块变更：验证契约、兼容性及直接受影响的调用方。
- 数据库变更：验证迁移脚本与数据兼容性，说明回退方式。
- 页面变更：实际操作相关用户流程，必要时提供截图证据。
- 依赖、构建或流水线变更：验证安装、构建或对应流水线实际可用。

根据实际改动和项目明确约定触发对应检查，说明其与本次任务的关系；无关专项检查不列为本次必过项。

## 发布 PR 追加检查

发布 PR 以 [按大需求选择性发布](../workflows/release.md) 确定的发布范围和 main 基线为准，完成以下检查及适用的构建、测试、验收、独立审查和专项检查：

1. 发布清单核对：选入的任务、提交和必要依赖准确，没有混入未完成需求。
2. 发布组合验证：对从 main 加上所选提交得到的实际代码组合，重新构建、联调和回归，覆盖本次大需求及直接受影响的既有功能。dev 的测试结果不能替代发布组合的验证。
3. 发布准备核对：所需配置、数据库脚本、发布顺序和回退说明齐全，完成大需求整体验收。

## 结果与证据

- 每项结果记录为通过、失败、未执行或不适用。不适用必须说明依据，不能将缺少环境、权限或运行失败记为不适用。
- 记录检查对应的提交 SHA、目标分支基线、运行命令或 CI 任务、实际结果，以及必要的输出或证据链接；将检查结果放入 PR 的 Evidence 部分。
- 必过项失败或未执行时，保持待处理或待验证状态，不计为通过；审查结论与检查结果分别记录。
- 既有失败通过目标分支基线对比说明，并记录按项目既定流程得出的处理结论。涉及必过项时，不能因为是既有失败而自动忽略或视为通过。

## 重跑与合并条件

- 证据必须对应最终待合并提交及目标分支基线。修复、rebase、cherry-pick 或发布清单变化后，重跑受影响检查，更新结果。
- 同一提交、同一目标分支基线已有可信 CI 结果时，可以复用，避免重复执行相同检查。
- 合并前核对所有适用的必过项均已通过，不适用项具有明确依据，独立审查没有未解决的有效阻塞项或必要验收的待验证项。
