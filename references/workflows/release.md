# 按大需求选择性发布

一个大需求对应一次版本发布。dev 允许同时集成多个大需求的开发任务；发布时，从最新 main 创建独立发布分支和 worktree，只选入本次大需求及必要依赖对应的改动，验收后通过 PR 合入 main。

开发任务的定义、独立分支与 worktree、任务 PR 合入 dev 的规则见 [Git 分支、worktree 与 PR 工作流](git.md)。本文件规定发布分支的基线与 PR 目标。

## 发布范围

- dev 用于多需求集成与联调，main 承载正式发布的代码。
- 一个大需求的所有开发任务完成并满足验收要求后，准备该需求的发布。
- 发布清单明确本次大需求、包含的任务、对应 PR、dev 上最终 squash 提交 SHA，以及必要依赖和应用顺序。
- 通过历次发布记录核对任务是否已经发布。cherry-pick 会产生新的提交，不能仅通过源 SHA 是否出现在 main 历史中判断任务是否已发布。
- 检查接口、公共代码、配置和数据库变更等依赖。仅在必要依赖已发布或可以作为独立验收的公共改动随本次发布时纳入清单。
- 如果本次需求依赖尚未完成、无法独立验收的其他需求，先拆出可独立发布的依赖任务，或暂缓本次发布；不能把未完成需求整体带入 main。

## 准备发布分支

1. 获取远端最新状态，核对最新 main 和发布清单。以下命令以 origin 为例，实际名称不同时替换为对应远端。
2. 从 origin/main 创建本次发布的独立分支和独立 worktree。继续已有发布时，复用对应分支、worktree 和 PR。
3. 在发布 worktree 中确认当前分支和发布基线。新建 worktree 应当干净；继续已有发布时，保留已有工作，先核对已选入清单、来源记录和进行中的 cherry-pick 或 rebase，处理当前操作后再继续。
4. 确认没有未完成的 Git 操作且工作区干净，按清单中的依赖顺序，仅补充尚未选入且尚未发布的任务提交。逐个 cherry-pick dev 上的任务 squash 提交，使用 -x 记录来源，并按 [代码提交信息规范](../standards/commit-messages.md) 保留源任务关联和破坏性变更说明。
5. 解决冲突时核对本次发布的业务意图和依赖，不引入清单之外的需求内容。存在冲突或提交为空时，先查清原因，再决定后续处理，不自动跳过提交。
6. 对照清单检查相对 main 的完整差异，包含必要代码、配置、数据库变更和文档。

新建发布的命令示例，执行前替换分支名、发布目录绝对路径和源提交 SHA。前两条命令在原仓库工作区执行，选入提交时显式指定发布 worktree：

```bash
git fetch origin
git worktree add -b "<发布分支>" "<发布目录绝对路径>" origin/main
git -C "<发布目录绝对路径>" cherry-pick -x "<任务在dev上的squash提交SHA>"
```

发布分支不能从 dev 创建，也不能把 dev 整体 merge、rebase 或 squash 到发布分支或 main；这些操作会携带其他需求的代码。发布清单始终保留源提交与任务的映射，即使冲突处理或后续合并改变了提交 SHA。

## 验证与发布 PR

1. 按 [合并前检查规范](../standards/pre-merge-checks.md) 执行发布 PR 的适用检查，在发布 worktree 或对应发布验证环境验证实际选出的代码组合。
2. 验收发现需要修复时，按开发任务流程先通过 PR 将修复合入 dev，再将修复的 squash 提交补入发布清单并 cherry-pick 到发布分支，重新验证。
3. 创建目标为 main 的发布 PR，正文使用仓库内的 [pr skill](../../.agents/skills/pr/SKILL.md)：Summary 包含发布清单和依赖说明，Evidence 包含实际发布代码组合的验证结果，Merge Danger 说明数据库与配置变更涉及的回退难度和影响范围。更新发布内容后，同步更新正文。
4. 提交 PR 和合并前再次获取最新 main。如果 main 已前进，在发布分支上 rebase 最新 origin/main，重新检查差异并验证。已推送分支的历史更新遵循 Git 工作流中的 --force-with-lease 规则。
5. 按 [代码审查与合并准入](../standards/code-review.md) 对发布清单及实际发布组合完成独立交叉验证与对抗性审查。审查和 [合并前检查](../standards/pre-merge-checks.md) 通过后，按项目约定的 main 分支合并方式合入发布 PR。开发任务向 dev 的 Squash and merge 要求不自动决定发布 PR 的合并方式。
6. 按项目现有流程执行版本发布，记录版本标识、发布 PR、实际部署的 main 提交和发布验证结果，并保留源任务映射供后续核对。

## 完成标准

- 本次发布有独立分支和 worktree，基于合并前最近一次获取的 main。
- 发布内容与清单一致，只包含本次大需求及已满足发布条件的必要依赖。
- 实际发布的代码组合通过项目要求的检查和验收。
- 发布 PR 已合入 main；实际部署提交、版本标识和发布后验证结果有记录。
- 开发任务合入 dev 表示集成完成；版本发布并验证成功，才表示该大需求发布完成。
